## 1. 構成案（ユーザー承認済み）

### できること
- iPhone/iPadのSafariでURLを開くと、インストール不要でその場で使える（ホーム画面に追加すれば全画面アプリ化も可能）
- 初回はGroq APIキーの取得手順（画面内リンク＋案内文）を見ながらキーを取得し、貼り付けるだけで使い始められる
- マイクボタンを押すと録音が始まり、話した内容が「認識中（薄いグレー）」→「確定（通常の黒字）」の2段階で表示される。認識中の文字は直前の確定文を踏まえて自動的に精度が上がる（文脈補正）
- 「A−」「A＋」ボタンで表示文字の大きさを変えられる
- 話している最中から、確定した文章は都度自動保存される。録音を止め忘れてアプリを閉じても、直前までの内容は消えずに残る
- 保存した会話をコピー・共有できる
- 新しい文字が増えると自動で最新行までスクロールする

### 画面の流れ
[画面1: 初回のみAPIキー取得・入力] → [画面2: メイン（録音ボタン＋文字表示＋文字サイズ操作）] → [画面3: 会話一覧] → [画面4: 過去の会話の詳細]

- 画面1: 「Groq APIキーの取得方法」の案内（console.groq.comへのリンク＋3ステップの手順文）、キー入力欄、「保存して始める」ボタン（初回のみ表示。以後は端末に記憶。画面2の設定からいつでも変更可）
- 画面2: 上部に文字サイズ操作（A−/A＋）、中央に大きな文字起こし表示エリア（認識中はグレー・確定は黒で視覚的に区別、自動スクロール）、下部に大きな録音ボタン（録音中は色が変わり脈動して「聞いている」ことが分かる）
- 画面3: 過去の会話をタイトル・日時で一覧表示
- 画面4: 選んだ会話の全文表示＋コピー/共有ボタン

### 作る順番（縦切り・セーブ地点付き）

🟢 セーブ地点①「マイク→Groq→文字表示が1回通った地点（walking skeleton）」
- この時点で画面で見えるもの: iPhoneのSafariで実際に録音し、話した内容が日本語テキストとして表示される。初回はGroq APIキーの取得手順が画面に案内される
- まだ無いもの: 連続的な区切り処理、下書き/確定の二段階表示、文脈補正、文字サイズ変更、保存機能
- ここまでは無駄にならない。かつ最大の技術リスク（CORS・iOS音声形式）をここで潰す

🟢 セーブ地点②「話し続けると自動で区切られ、下書き→確定の二段階で逐次表示される地点」
- この時点で画面で見えるもの: 1分間話し続けると、認識中の文字がグレーで先に出て、確定すると黒字に変わりながら文章が追記されていく。認識精度は直前の確定文を踏まえて自動的に上がる（文脈補正）。新しい文字が増えると自動スクロールする。Groqの利用制限に達したら送信を止めて画面に告知
- まだ無いもの: 文字サイズ変更、画面消灯防止、保存機能

🟢 セーブ地点③「文字サイズが変わり、画面が消えなくなった地点」
- この時点で画面で見えるもの: A−/A＋ボタンで文字が大きく/小さくなる。録音中は画面が自動で暗くならない
- まだ無いもの: 保存機能、PWA化

🟢 セーブ地点④「会話が逐次保存され、後から見返せる地点」
- この時点で画面で見えるもの: 話すたびに確定した文章がその場で保存され、録音を止めなくても、途中でアプリを閉じても一覧に残る。過去の会話を開いてコピー・共有できる
- まだ無いもの: ホーム画面アイコン化

🟢 セーブ地点⑤「ホーム画面に追加して全画面アプリとして起動する地点」
- この時点で画面で見えるもの: ホーム画面のアイコンから起動すると、Safariのアドレスバーが無い全画面アプリとして動く
- まだ無いもの: なし（完成）

### 危険ポイント（ここで方針を変えると大きく戻る）
- セーブ地点①でGroq APIへのブラウザ直叩き（CORS）が通らないと判明した場合、中継サーバーを挟む構成に変わる（実装の大枠は変わらないが公開手順が増える）
- セーブ地点①で採用する録音のファイル形式（後述）は、以降すべてのStepの土台になる。ここを後から変えると録音まわりを作り直しになる

### この設計の安全網
- 各セーブ地点で2か所に保存する: ①Git履歴（「巻き戻して」で戻せる）②フォルダ丸ごとコピー
- 詰まったStepがあれば A) 飛ばす／B) もっと簡単に／C) 別セッションで相談 の3択を提示する

## 2. 技術選定（AIが決定）

選定原則: サーバーを持たない・依存を増やさない・iOS Safari で確実に動く組み合わせを最優先する。ACS（`resources/app/renderer/app.js`）のリアルタイム文字起こし実装を移植元とする。

| 項目 | 採用 | 理由（1行） |
|------|------|-----------|
| 動かす場所 | iPhone/iPad の Safari（PWA） | ネイティブアプリ化はApple開発者登録・審査が要り自分用には過剰 |
| 言語・ランタイム | Vanilla HTML/CSS/JS（ビルド無し） | ビルド工程を挟むとGitHub Pagesへの公開手順が増え、依存予算=0の原則に反する |
| 録音API | `MediaRecorder`（mimeType: `audio/mp4`） | iOS Safariは`audio/webm`非対応。`audio/mp4`(AAC)が確実に動く唯一の選択 |
| 文字起こし | Groq API 直叩き（`whisper-large-v3`） | ACSと同じモデル・同じ発想。サーバー不要でユーザー指定の「Groq APIキーを使う」要件に合致 |
| チャンク方式 | 録音器を都度作り直す方式（ACS方式を移植） | `timeslice`指定の複数`dataavailable`はiOSで単体デコード可能な断片になる保証がなく、Groqへの送信単位として不確実 |
| 認識精度の底上げ | Groq Whisperの`prompt`パラメータに直前の確定済みテキスト（末尾200字程度）を渡す（ACSの`contextText`方式を移植） | 学習済みの専用モデルを別途用意せず、API標準機能だけで文脈補正が効く。追加コスト・依存ゼロ |
| 表示の二段階化 | 認識中は「draft」区分（薄いグレー表示）、確定後は「confirmed」区分（通常色）に置き換え | ACSの`seg-draft`/`seg-confirmed`実装と同じ発想。ユーザーが「今どこまで確定したか」を視覚的に把握できる |
| テキスト整形 | 確定直後にクライアント側の純粋関数で軽い後処理（連続する重複語の除去・句読点の正規化）のみ行う | Groqの生出力を尊重しつつ、明らかなノイズだけ除去する。意味を変える強い修正（言い換え・要約）はしない方針（過剰編集で誤情報化するリスクを避ける） |
| データ保存 | IndexedDB（会話本体）＋localStorage（APIキー・文字サイズ設定） | 会話は量が増えるためIndexedDB、単一値の設定はlocalStorageで十分（過剰設計を避ける） |
| ホスティング | GitHub Pages（公開リポジトリ） | コードに秘密が一切入らない設計のため公開で問題ない。無料・URLが安定・自分用に十分 |
| 画面消灯対策 | Wake Lock API（`navigator.wakeLock`） | 標準APIで依存追加なし。非対応時は「画面を点けたままに」の文言でフォールバック |
| 認証 | なし（URLを知っていれば誰でも開けるが、APIキーはアプリに同梱しないため実害は小さい） | 公開範囲=自分用の結論に対応。プロキシ常設は不要と判断 |

**捨てた案と理由（ADRの種）**
- 自前プロキシサーバー常設: CORSが通ればブラウザ直叩きで完結するため、常時稼働のサーバーコストは不要と判断（採用条件: Step1でCORS不可と判明した場合のみ、Cloudflare Workers無料枠で30行程度の中継に切替）
- ネイティブiOSアプリ（Swift）: 開発者登録・審査・Xcode環境が要り、自分用アプリには投資が見合わない
- `timeslice`による定期分割: iOS実機での断片デコード可否が未検証で、walking skeletonの段階で不確実性を1つ増やすため、ACSで実績のある「作り直し方式」を初手から採用

## 2.5 NFR速査表

| 項目 | 決めること |
|------|-----------|
| データ喪失の許容 | 会話はiPhone内のIndexedDBのみに保存。自動クラウド同期は作らない（YAGNI）。失いたくない会話は「共有」ボタンで手動エクスポートする運用 |
| 性能の目安 | 発話が止まってから文字が表示されるまで3秒以内を目安。超える場合は「処理中…」表示でユーザーを待たせない |
| 秘密情報 | Groq APIキーは`localStorage`にのみ保存。コード・console.log・URLパラメータに絶対に出さない |
| 可観測性 | `console.log`で最低限（録音開始/停止・API呼び出し成否・429検知）を出す。外部送信するログ基盤は持たない |
| 配布性 | GitHub Pages公開URL1本。iPhone/iPadのSafariで開けば追加インストール無しで動作する条件を完了判定に含める |

## 2.6 依存予算

- npmパッケージ: **0個**。`getUserMedia` / `MediaRecorder` / `fetch` / `IndexedDB` / `Wake Lock API` / `Service Worker` はすべてブラウザ標準
- 開発時のみ、ローカルプレビュー用に `npx serve` 等をその場で使うことがあるが、`package.json`には入れない（配布物に依存が残らないようにする）
- 従量課金APIはGroqのみ。Step1で実送信の前に、送信予定のURL・パラメータをconsole出力するdry-run確認を1回行ってから実送信する（グローバルCLAUDE.md §F8準拠）

## 3. Step詳細（垂直スライシング）

### Step 0: プロジェクト初期化
- プロジェクトフォルダ `C:\Projects\realtime-transcribe-ios\` を作成する
- `.gitignore` を最初に作る（`.env`を除外。今回サーバーサイドコードは無い予定だが将来Cloudflare Worker中継に切り替わる可能性に備えて先に除外設定しておく）
- **memory-init スキルを実行**して `.claude/memory/` を初期化する
- `git init` → 初回コミット → タグ `step-0-done`
- 完了判定: `git log`に初回コミットが1件、`git status`で`.env`が追跡されておらず、`.claude/memory/`が存在すること

### Step 1: マイク→Groq→文字表示が1回通る（walking skeleton）
- ユーザーから見えるゴール: iPhoneのSafariでページを開き、Groq APIキーを入力→録音ボタンを押して5秒話す→止めると日本語のテキストが画面に表示される
- 技術: `index.html` / `app.js` / `style.css`の最小構成。`getUserMedia`→`MediaRecorder(audio/mp4)`→停止時に`fetch`でGroq `/openai/v1/audio/transcriptions`へPOST（`model=whisper-large-v3`, `language=ja`）
- 作業:
  - APIキー取得手順の案内UIを作る（`console.groq.com/keys`へのリンク＋「①アクセス②ログイン③Create API Keyでキーを作成④コピーして下に貼り付け」の3〜4ステップ文。取得手順自体はGroq側の画面なのでこちらはリンクと文言案内のみ）
  - APIキー入力欄を作り、`localStorage`に保存する（値をログ・URLに絶対出さない）
  - 録音開始/停止ボタンを作る
  - 停止時に録音Blobを`multipart/form-data`でGroqへ送信し、結果テキストを画面に表示する
  - dry-run確認: 実送信前に、送信予定のURL・ヘッダー名（Authorizationの値は伏せる）・パラメータをconsoleに出して1回確認する
  - GitHub Pagesへ公開し、iPhone実機のSafariで開いて検証する（ここで最大リスク仮定1・2を潰す）
- 完了判定（目視）: iPhoneの実機Safariでキー取得案内を見ながらキーを設定でき、実際に日本語音声を録音すると文字が表示される
- 完了判定（スモーク）: `node test/smoke-groq.mjs`（ダミーwav音声ファイルをGroqへ送信し200が返ることをNode側から機械確認）が緑
- Step完了処理: **step-complete スキルを実行**（セキュリティチェック→git-save→タグ`step-1-done`→マージ提案）
- 見積り時間: 3時間
- 撤退線: 6時間を超えたら停止して再計画。特にCORSで詰まったら試行錯誤せず、即座にCloudflare Worker中継案へ切替を提案する
- セーブ② フォルダコピー: `realtime-transcribe-ios_backup/2026-09-01_step1完了/`

### Step 2: 話し続けると自動で区切られ、下書き→確定の二段階で逐次表示される
- ユーザーから見えるゴール: 1分間話し続けると、認識中の文字がグレーで先に表示され、確定すると黒字に変わりながら文章が追記されていく。Groqの利用制限（429）に達したら送信を止めて「後でお試しください」と1回だけ表示する
- 技術: 音量ベースの簡易VAD（`AnalyserNode`で無音区間を検出）。無音を検出したら録音器を止めて新しい録音器を作り直す方式（ACSの`draftTimer`相当をVanilla JSへ移植）
- 作業:
  - VAD監視ループを実装し、無音検出で1チャンクを確定候補としてGroqへ送信
  - 送信中〜応答前は「draft」区分（薄いグレー・`<span class="seg-draft">`相当）で仮表示し、応答が返ったら「confirmed」区分（通常色）に置き換える（ACSの二段階表示を移植）
  - Groq呼び出し時、`prompt`パラメータに直前の確定済みテキスト（末尾200字程度）を渡し、認識精度を文脈で底上げする（ACSの`contextText`方式）
  - 確定直後に軽いテキスト整形（連続する重複語の除去・句読点の正規化）を行う純粋関数を通す。言い換え・要約はしない
  - 新しい行が追加されるたびに表示エリアを自動スクロールする
  - 429検出時は送信フラグを落として以後の自動送信を止め、画面に1回だけ告知する（ACSで未着手だったGroq教訓をここで先取り実装する）
- 完了判定（目視）: iPhone実機で1分間話し続け、グレーの認識中文字→黒字の確定文字という順で区切りごとにテキストが増え、自動スクロールする
- 完了判定（スモーク）: VAD判定ロジック（無音検出の閾値計算）とテキスト整形関数を純粋関数へ切り出し、`node test/smoke-vad.mjs`でダミーの音量配列・重複テキストを渡して判定結果を確認
- Step完了処理: step-complete スキル実行（タグ`step-2-done`）
- 見積り時間: 3時間
- 撤退線: 6時間
- セーブ②: `realtime-transcribe-ios_backup/2026-09-01_step2完了/`

### Step 3: 文字サイズ変更・画面消灯防止

### Step 4: 会話の逐次自動保存・一覧・書き出し
- ユーザーから見えるゴール: 話すたびに確定した文章がその場でIndexedDBへ書き込まれる。録音を止め忘れてアプリを閉じたり、iPhoneの都合でSafariがページを破棄しても、直前までの内容は一覧に残っている。一覧画面から過去の会話を開き、コピー・共有できる

- 完了判定（スモーク）: IndexedDBラッパーのCRUD＋逐次追記ロジックを`node test/smoke-db.mjs`で確認（`fake-indexeddb`等は依存予算に反するため、保存対象データの整形・ID生成など純粋関数部分のみを切り出してテストする）
- Step完了処理: step-complete スキル実行（タグ`step-4-done`）
- 見積り時間: 3時間

## 4. 想定される地雷と対処

- 地雷1（最大リスク仮定1）: Groq APIがブラウザからの直接呼び出し（CORS）を許可しない
  - 対処: Step1で実機検証。不可なら試行錯誤せずCloudflare Workers（無料枠）による軽量中継へ即切替
- 地雷2（最大リスク仮定2）: iOS Safariの`MediaRecorder`が想定通りの完全ファイル単位でチャンクを生成しない
  - 対処: Step1で実機検証。ACS実績の「録音器を都度作り直す」方式を厳守し、`timeslice`による分割は使わない
- 地雷3: Wake Lock APIが非対応の古いiOSバージョンで動かない
  - 対処: 機能検出で分岐し、非対応時は「画面を点けたままにしてください」の文言でフォールバック（Step3）
- 地雷4: Groqの無料枠はACSの実測で「1日あたりのリクエスト回数(RPD 2000)」が先に尽きることが判明済み（`~/.claude`側の記憶: 音声時間表記は誤り）
  - 対処: Step2で429検出時に自動送信を停止し1回だけ告知する設計を初手から組み込む（ACSでは未着手だった対策をここで先取り）
- 地雷5: iOS Safariのプライベートブラウズモードでは IndexedDB の永続化が制限される
  - 対処: 通常のSafariモード（プライベートでない）を前提とし、完了判定もそのモードで行う旨を明記するに留める（自分用アプリのため過剰対応しない）
- 地雷6: Whisper系モデルは`prompt`（文脈）を渡すと、まれにその文脈に引きずられて実際には話していない単語を出力する（ハルシネーション）ことが知られている
  - 対処: `prompt`に渡すのは直前の確定テキストの末尾200字程度に限定し、長大な文脈は渡さない。テキスト整形は「重複除去・句読点正規化」の機械的処理のみに留め、意味を書き換える強い自動修正（言い換え・要約・誤字の推測変換）はしない。将来「修正が多すぎる/精度が下がった」と感じたら`prompt`を渡さない設定に切り替えられるようにする
- 地雷7: iOS Safariはメモリ不足時や長時間の非アクティブでページ自体を破棄することがあり、「録音終了時に一括保存」の設計だと直前までの内容が丸ごと消える
  - 対処: Step4で「確定セグメントが生まれるたびに逐次IndexedDBへ書き込む」設計にし、録音終了操作を前提にしない。停止し忘れ・タブ切り替え・不意の終了でも記録が残ることを完了判定に含める

## 4.5 実装の進め方（実装セッション向けルール）

- まずMVP（Step1のwalking skeleton）を作る。全機能を一度に作らない

- 各関数の冒頭に「何をする関数か」を日本語コメントで書く

4. エラーが出たら「○○が原因でした」と平易に説明してから修正・再実行

## 7. セキュリティ方針

- Groq APIキーは`localStorage`のみで管理。コード・ログ・URLに露出させない
- 機密情報をソースコードに埋め込まない（GitHub Pages公開リポジトリのため特に厳守）
- ユーザー入力（会話テキスト）を表示する際はエスケープする（XSS対策）
- 各Stepコミット前に`git diff`でAPIキー文字列（`gsk_`等の接頭辞）が含まれていないか確認
- 外部への通信はGroq APIへの音声送信のみ。他に何も送らない
